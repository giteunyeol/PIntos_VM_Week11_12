V9 mmap Syscall Entry / Validation 러버덕 정리

V9의 핵심은 mmap의 실제 lazy loading을 완성하기 전에, syscall 입구에서 "이 요청은 받아도 되는 요청인가?"를 걸러내는 것입니다. 이 문서는 오리에게 말로 설명하듯 각 검증 조건이 왜 필요한지, 어디서 확인하는지, 어떤 테스트와 연결되는지 정리합니다.

내가 맡은 범위

SYS_MMAP, SYS_MUNMAP entry 연결과 mmap 인자 검증입니다.

성공 목표

잘못된 mmap 요청은 MAP_FAILED, 즉 NULL을 반환하게 만듭니다.

핵심 파일

syscall.c, file.c, file.h, vm.h를 봅니다.

대표 테스트

mmap-null, mmap-zero-len, mmap-misalign, mmap-bad-fd*, mmap-bad-off.

한 문장 요약

mmap(addr, length, writable, fd, offset)는 "파일 fd의 내용을 사용자 가상주소 addr부터 length만큼 매핑해줘"라는 요청이고, V9는 이 요청이 말이 되는 요청인지 먼저 검사하는 단계입니다.

사용자 프로그램 -> mmap() -> syscall5(SYS_MMAP, addr, length, writable, fd, offset) -> syscall_handler() -> do_mmap()

1. syscall 인자 위치

Pintos x86-64 syscall wrapper는 인자를 레지스터에 넣습니다. 이 저장소의 intr_frame에서도 r10이 네 번째 인자라고 주석이 달려 있습니다.

mmap 인자 레지스터 syscall_handler에서 읽는 곳 뜻
addr rdi f->R.rdi 매핑을 시작할 사용자 가상주소
length rsi f->R.rsi 매핑할 바이트 수
writable rdx f->R.rdx 쓰기 가능한 mapping인지
fd r10 f->R.r10 매핑할 열린 파일 descriptor
offset r8 f->R.r8 파일 안에서 시작할 offset

V9-E fd 0/1 및 bad fd reject "0은 stdin, 1은 stdout이야. 얘들은 일반 파일이 아니니까 mmap 대상이 아니야. fd_list에 없는 숫자도 당연히 거절." NULL mmap-bad-fd, mmap-bad-fd2, mmap-bad-fd3
V9-F offset page-aligned 검사 "파일의 중간부터 매핑할 수는 있지만, offset도 page 단위여야 해. 0x1234 같은 값은 page 경계가 아니야." NULL mmap-bad-off
V9-G mapping range overlap 검사 "addr 한 페이지뿐 아니라 length가 덮는 전체 page 범위를 봐야 해. 그중 하나라도 이미 SPT에 있으면 겹치는 매핑이야." NULL mmap-overlap, 이후 overlap 계열

3. 검증 순서

1

syscall switch에 case 추가

SYS_MMAP에서는 인자 5개를 꺼내고, SYS_MUNMAP에서는 주소 1개를 꺼냅니다.

2

가벼운 값 검증 먼저

addr == NULL, pg_ofs(addr) != 0, length == 0, offset % PGSIZE != 0 같은 조건을 먼저 봅니다.

3

fd로 파일 찾기

fd < 2는 바로 실패. 그 외에는 find_fd_entry(fd)로 struct file *을 찾습니다.

4

주소 범위 전체 검사

[addr, addr + length)가 사용자 주소이고, 각 page가 SPT에 이미 없는지 확인합니다.

5

진짜 mmap 구현으로 넘기기

모든 검증을 통과하면 do_mmap(addr, length, writable, file, offset)로 넘깁니다.

4. 오리와 대화하기

나: mmap 요청이 들어왔어. 제일 먼저 뭘 볼까?

오리: syscall 번호가 SYS_MMAP인지 switch에서 잡히는지 봐. case가 없으면 아무 검증도 못 해.

나: 주소가 NULL이면 왜 안 돼?

오리: Pintos는 0번 page 매핑을 금지해. null pointer 접근을 잡아야 하는데 거기에 파일을 매핑하면 위험해져.

나: 주소 정렬은 왜 중요해?

오리: VM은 page 단위로 움직여. 시작 주소가 page 경계가 아니면 SPT key, PML4 mapping, file offset 계산이 다 애매해져.

나: fd 0, 1은 왜 reject야?

오리: stdin/stdout은 일반 파일 객체처럼 page에 매핑할 수 있는 대상이 아니야. mmap은 파일 내용을 메모리처럼 보이게 하는 기능이야.

나: overlap은 뭘 기준으로 봐?

오리: 시작 주소 하나만 보지 말고, length가 덮는 모든 page를 봐. 하나라도 SPT에 이미 있으면 실패야.

6. 테스트별로 어떤 조건을 때리는가

테스트 요청 모양 내 코드가 잡아야 하는 조건
mmap-null mmap(NULL, 4096, ..., fd, 0) addr == NULL이면 MAP_FAILED
mmap-zero-len mmap(addr, 0, ..., fd, 0) length == 0이면 MAP_FAILED
mmap-misalign mmap(0x10001234, 4096, ..., fd, 0) pg_ofs(addr) != 0이면 MAP_FAILED
mmap-bad-fd 존재하지 않는 fd find_fd_entry(fd) == NULL이면 MAP_FAILED
mmap-bad-fd2 fd == 0 stdin은 mmap 대상이 아니므로 MAP_FAILED
mmap-bad-fd3 fd == 1 stdout은 mmap 대상이 아니므로 MAP_FAILED
mmap-bad-off offset == 0x1234 offset % PGSIZE != 0이면 MAP_FAILED
mmap-overlap 이미 매핑된 주소에 다시 mmap range 안의 page가 SPT에 이미 있으면 MAP_FAILED

내가 구현할 때 체크리스트

  • SYS_MMAP, SYS_MUNMAP case가 switch문에 있는가?
  • fd를 f->R.r10에서 읽고 있는가?
  • offset을 f->R.r8에서 읽고 있는가?
  • 실패 조건에서 f->R.rax = (uint64_t) MAP_FAILED 또는 NULL을 넣는가?
  • addr, length, fd, offset 검사를 do_mmap() 호출 전에 하는가?
  • overlap 검사는 시작 page 하나가 아니라 전체 range를 보는가?
  • 검증 실패 시 file을 건드리거나 SPT에 page를 넣지 않는가?

나중 단계와 헷갈리지 말 것

  • V9는 validation입니다. 실제 VM_FILE page를 만들고 lazy loading하는 코드는 다음 단계의 본체입니다.
  • do_mmap() 안에서도 검증을 한 번 더 해도 됩니다. syscall 입구와 구현 함수 사이의 방어선이라고 생각하면 됩니다.
  • bad fd 테스트 설명에는 "fail silently or terminate"라고 되어 있지만, 여기서는 조용히 MAP_FAILED를 반환하는 방향이 가장 덜 위험합니다.
  • file length가 0인 경우도 보통 실패 처리합니다. V9 표에는 없지만 이후 mmap 테스트에서 도움이 됩니다.
